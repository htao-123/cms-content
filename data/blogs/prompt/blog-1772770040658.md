好，我直接给你一套 **可落地的标准模板**。
这套是按你前面提到的场景整理的，目标是让 AI coding 更稳定：

* 不只改前端
* 不漏后端
* 不乱重构
* 不跳过交互设计
* 不修一个问题引出一串新问题

你可以把它理解成一套 **团队级标准模式**。

---

# 一、总模板：通用任务标准模式

这个模板适合大多数开发任务，先给总版。

```markdown
# Task

## Problem
清晰描述当前问题或需求。
包含用户操作路径、触发条件、当前结果、期望结果。

## Context
说明项目上下文：
- 涉及的端：web / mobile / desktop / backend
- 涉及的仓库或模块
- 当前功能链路
- 已知限制或历史实现方式

## Expected Behavior
明确修复或实现完成后的行为：
1. 用户应该看到什么
2. 系统应该如何处理
3. 失败时如何提示
4. 是否需要支持重试 / 幂等 / 进度反馈

## Constraints
必须遵守的约束：
1. 必须从全链路视角分析，不能只改前端
2. 必须评估是否涉及后端、数据库、任务机制、消息机制
3. 不允许引入临时 mock 逻辑
4. 不允许破坏现有功能
5. 所有失败提示统一使用 dialog（如果这是当前规范）

## Architecture Check
在动手前必须先判断：
1. 这个需求是否只涉及前端
2. 是否需要后端接口配合
3. 是否需要数据结构调整
4. 是否需要异步任务 / 定时任务 / MQ / 状态机
5. 是否涉及多端一致性

## UI / UX Check
在改代码前先给出：
1. 页面/状态变化说明
2. 关键交互流
3. 加载态、空态、失败态
4. 成功后的反馈方式
5. 如果涉及前端改动，先给交互方案，再实现代码

## Implementation Guidance
优先按以下顺序分析：
1. 根因
2. 架构影响范围
3. 最小可行修复路径
4. 风险点
5. 回归检查点

## Deliverables
输出必须包含：
1. 问题根因
2. 改动方案
3. 涉及模块
4. 风险说明
5. 回归检查清单
```

# 二、Bug 修复模板

这个适合你们最常见的“修问题”。

```markdown
# Bug Fix Task

## Problem
当用户【具体操作】时，出现【具体异常】。

复现路径：
1. ...
2. ...
3. ...

当前结果：
- ...

期望结果：
- ...

## Context
涉及模块：
- Frontend:
- Backend:
- Mobile/Desktop:
- API:
- 数据表/任务机制（如有）:

## Expected Behavior
1. 修复该问题
2. 给出明确根因
3. 不引入新的问题
4. 所有失败提示遵循现有规范
5. 涉及异步流程时，需要明确状态反馈

## Constraints
1. 必须先分析根因，再修改代码
2. 不允许只修表层 UI，必须检查真实链路
3. 如果问题可能涉及后端/接口/数据，必须一起检查
4. 不允许为了修复而绕过已有架构
5. 修复后要做一轮全链路审查

## Required Checks
请重点检查：
- 参数传递是否正确
- 状态管理是否一致
- 接口返回处理是否完整
- 边界数据量是否会触发异常
- 错误提示是否统一

## Deliverables
输出：
1. 根因分析
2. 修复方案
3. 修改点
4. 风险点
5. 回归建议
```

# 三、新功能开发模板

适合“做一个新功能”，避免 AI 直接一头写代码。

```markdown
# Feature Task

## Goal
实现【功能名称】。

## Business Background
说明这个功能解决什么问题，服务什么用户场景。

## Context
涉及范围：
- Web:
- Mobile:
- Desktop:
- Backend:
- 数据层:
- 第三方服务（如有）:

## Expected Behavior
1. 用户进入什么页面
2. 做什么操作
3. 系统如何响应
4. 成功时如何反馈
5. 失败时如何提示
6. 是否支持中断、重试、恢复

## Architecture Check
实现前必须先判断：
1. 是否需要新增接口
2. 是否需要新增字段/表/状态
3. 是否需要任务队列 / 定时扫描 / 批处理
4. 是否涉及多端同步
5. 是否需要权限控制

## UI / UX Check
先输出：
1. 页面结构
2. 交互流
3. 状态设计（加载中、处理中、部分成功、失败）
4. 大数据量场景下的交互反馈
5. 多端体验是否一致

## Constraints
1. 不允许只做前端展示层
2. 必须评估完整业务闭环
3. 必须考虑异常场景
4. 必须考虑后续扩展性
5. 不允许引入明显的性能隐患

## Deliverables
1. 方案设计
2. 架构影响范围
3. 实现步骤
4. 风险评估
5. 回归清单
```

# 四、架构评审模板

这个就是你前面提到的那种：
“现在这个架构到底对不对？”

```markdown
# Architecture Review Task

## Problem
当前方案是：
- ...

我的疑问是：
- ...

例如：
- 为什么由 data 调 relation？
- 为什么用 MQ 而不是定时扫描？
- 大批量数据是否会导致消息积压？

## Review Scope
请从以下维度评审：
1. 业务合理性
2. 架构职责边界
3. 性能与吞吐
4. 失败恢复能力
5. 运维复杂度
6. 后续扩展性

## Required Analysis
必须回答：
1. 当前架构的核心问题是什么
2. 当前职责划分是否合理
3. MQ 是否适合当前场景
4. 定时任务 / 扫描机制是否更合适
5. 大批量数据下会出现什么问题
6. 如何保证幂等、可恢复、可观测

## Constraints
1. 不能只从代码实现角度回答，必须从系统架构角度回答
2. 要结合数据量级分析
3. 要明确指出当前方案的优点和问题
4. 给出推荐方案和不推荐方案
5. 说明取舍原因

## Deliverables
1. 当前架构评价
2. 风险分析
3. 推荐方案
4. 演进路径
5. 注意事项
```

# 五、代码审查模板

适合你说的“再做一轮全链路审查”。

```markdown
# Code Review Task

## Scope
请审查本次改动，范围包括：
- 功能正确性
- 架构合理性
- 多端影响
- 性能风险
- 错误处理
- 回归风险

## Review Focus
重点检查：
1. 是否只改了前端而漏了后端
2. 是否存在状态不一致
3. 是否有边界场景未覆盖
4. 是否会影响现有功能
5. 是否符合当前项目规范
6. 是否存在明显性能问题
7. 是否有失败后无法恢复的问题

## Constraints
1. 必须基于全局架构视角审查
2. 不要只看局部代码
3. 明确指出高风险点、中风险点
4. 给出建议修复方案
5. 不要泛泛而谈

## Deliverables
输出：
1. 审查结论
2. 问题清单
3. 风险等级
4. 建议修改项
5. 是否建议合并
```

# 六、多端联动模板

这个很适合你们，因为你经常会遇到 web / mobile / desktop / backend 一起动。

```markdown
# Cross-Platform Task

## Problem
描述功能或问题。

## Platforms
本次必须检查以下端是否受影响：
- Web
- Mobile
- Desktop
- Backend
- Admin（如有）

## Required Analysis
请逐端判断：
1. 是否需要改动
2. 改动点是什么
3. 是否存在体验不一致
4. 是否需要接口兼容
5. 是否涉及共享状态或同步机制

## Constraints
1. 不允许默认认为只涉及某一端
2. 必须显式说明哪些端不受影响，以及原因
3. 如果某端不改，也要给出判断依据
4. 必须考虑跨端一致性

## Deliverables
输出：
1. 影响范围矩阵
2. 每端改动建议
3. 风险点
4. 联调建议
```

# 七、大数据量任务模板

这个适合你前面提到的“20万条删除”“几十万导入”。

```markdown
# Large-Scale Data Task

## Problem
当前需求涉及大批量数据处理，数据量级约为：
- ...

## Expected Behavior
1. 用户可以发起批量操作
2. 系统可以持续处理
3. 即使部分失败，用户也能继续后续操作
4. 要能告诉用户失败原因
5. 用户应感知到数据在逐渐变化

## Required Analysis
必须分析：
1. 同步处理是否可行
2. 是否需要分批
3. 是否需要任务状态
4. 是否需要幂等机制
5. 如何处理中断、失败、重试
6. 如何做前端进度反馈
7. 如何保证用户可继续操作剩余数据

## Constraints
1. 不允许设计成一次性全量硬删且不可恢复
2. 不允许只有后端处理但前端无状态反馈
3. 必须考虑部分完成、部分失败
4. 必须考虑可观测性和告警
5. 必须说明性能与资源风险

## Deliverables
1. 处理流程
2. 状态机设计
3. 用户反馈机制
4. 失败恢复机制
5. 风险说明
```

# 八、你最需要加进 skill 里的“硬约束”

这一段我很建议你直接放进全局 skill，当作固定规则。

```markdown
# Global Engineering Rules

1. 所有任务必须先做全链路分析，再修改代码。
2. 不允许默认只改前端，必须评估是否涉及后端、数据层、任务机制和多端同步。
3. 任何涉及 UI 交互变化的任务，必须先给出交互方案或状态说明，再进入实现。
4. 所有失败提示必须遵循项目统一规范，不允许随意使用不同提示方式。
5. 对于批量任务、大数据量任务、异步任务，必须考虑：
   - 分批处理
   - 幂等
   - 失败恢复
   - 进度反馈
   - 用户可继续操作
6. 修复问题时不能只修表象，必须分析根因。
7. 修改完成后必须再做一轮全链路审查，检查是否引入新问题。
8. 如果某个需求只涉及某一端，也必须显式说明为什么其他端不受影响。
9. 不允许通过临时 mock、绕过接口、硬编码状态来伪造功能完成。
10. 输出时必须包含：根因/方案/影响范围/风险/回归检查。
```

# 九、最适合你现在使用的简化版

如果你嫌上面太长，你可以用这个精简版。
这是我最推荐你日常直接发给 AI 的版本。

```markdown
请按以下规范执行本次任务：

1. 先分析问题根因，不要直接改代码。
2. 从全链路视角评估本次需求，明确是否涉及前端、后端、数据层、任务机制和多端影响。
3. 如果有 UI 交互变化，先给出交互方案和关键状态设计，再实现代码。
4. 不允许只做前端表层修复，必须检查真实业务链路。
5. 对于失败场景，必须说明提示方式，并遵循项目统一规范。
6. 对于大数据量或异步任务，必须考虑分批、进度、失败恢复和可继续操作能力。
7. 修改后再做一轮全链路审查，确保没有引入新的问题。
8. 输出必须包含：
   - 根因分析
   - 方案说明
   - 涉及模块
   - 风险点
   - 回归检查项
```

# 十、怎么组合成你自己的团队版

我建议你最终整理成 3 层：

**第 1 层：全局规则**
放你刚才关心的那些硬约束。

**第 2 层：任务模板**
Bug / 新功能 / 架构评审 / Code Review。

**第 3 层：项目特定规则**
比如：

* jotmo-frontend 规范
* jotmo-backend 规范
* mobile build 规范
* 所有失败提示必须是 dialog
* 涉及前端改动必须先给交互图

这样 AI 基本就不容易跑偏。

# 十一、我给你的直接可用版本

下面这段你几乎可以直接拿去当全局 skill 提示词：

```markdown
你是该项目的 AI 工程助手。所有任务必须遵循以下规则：

1. 先分析，再实现。不要直接写代码。
2. 必须从全链路架构视角思考问题，明确是否涉及前端、后端、数据层、任务机制、消息机制、多端同步。
3. 不允许默认只改前端。凡是 UI 交互依赖真实业务状态的功能，都必须评估后端和数据层是否需要配合修改。
4. 涉及 UI 改动时，必须先给出交互方案，说明页面状态、加载态、失败态、成功态，再进入代码实现。
5. 所有失败提示必须遵循项目统一规范；如果当前规范要求使用 dialog，则统一使用 dialog。
6. 对于批量任务、大数据任务、异步任务，必须考虑分批处理、幂等、失败恢复、进度反馈、可继续操作能力。
7. 修复问题时必须分析根因，不允许只修表层现象。
8. 修改完成后，必须再做一轮全链路审查，确认没有引入新的问题，并检查多端和上下游影响。
9. 如果判断某些端不需要改动，也必须明确说明原因。
10. 输出时必须包含：根因分析、方案说明、涉及模块、风险点、回归检查项。
```
